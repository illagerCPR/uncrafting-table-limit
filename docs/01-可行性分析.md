# Uncrafting Table Limit —— 可行性分析

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 已完成（2026-10-12），全部结论基于对 Twilight Forest 发布版 jar 与源码的实读核对 |
| 目标 | 为 Minecraft 1.21.1 / NeoForge 的暮色森林附属模组「拆解台限制」提供技术闸门结论 |
| 结论 | **可行**。三条主线（全局冷却 / 禁止拆解 / 使用耐久）均有确定的实现路径，无阻塞性风险 |

---

## 1. 需求与目标

给暮色森林（The Twilight Forest）的**拆解台（Uncrafting Table）**加限制，用于服务器平衡：默认全局冷却，另提供若干**互斥**的限制方法，通过配置**单选**生效。

| 编号 | 限制方法 | 语义 | 默认 |
| --- | --- | --- | --- |
| A | 全局冷却（`COOLDOWN`） | 每次拆解成功后，玩家需等待 N ticks 才能再次拆解 | **默认启用，24000 ticks（=1 游戏日 / 20 分钟）** |
| B | 禁止拆解（`DISABLED`） | 拆解台可打开、可预览，但不能取出任何拆解产物 | 可选 |
| C | 使用耐久（`DURABILITY`） | 每座拆解台有耐久，每次拆解消耗若干点，耗尽后销毁或失效 | 可选 |
| D | 物品代价（`ITEM_COST`） | 每次拆解额外消耗玩家物品栏中的指定物品若干 | 可选（附加方法，见 §4.4） |

**互斥规则**：`mode` 为单一枚举配置项，同一时刻只有一种方法生效。

### 1.1 首版不做

- 不做客户端 GUI 倒计时/耐久条渲染（首版用服务端动作栏文字反馈）
- 不做拆解台以外任何方块的限制
- 不修改暮色森林自身的配置文件或网络协议
- 不提供绕过路径的"管理员白名单"（后续如需再评估）

### 2.2 拆解台的实现结构（发布版 jar 逐类核对）

```
twilightforest:uncrafting_table  (UncraftingTableBlock extends Block)
  └─ useWithoutItem(...)  ──► player.openMenu(getMenuProvider(...))
        └─ SimpleMenuProvider  ──► new UncraftingMenu(id, inv, level, ContainerLevelAccess.create(level, pos))

twilightforest:uncrafting  (MenuType<UncraftingMenu>, 工厂 UncraftingMenu::fromNetwork)
  UncraftingMenu extends RecipeBookMenu
    ├─ 槽位布局（共 56 槽）
    │    0        : tinkerInput          （放待拆解物品）
    │    1        : UncraftingResultSlot （拆解产物/重铸产物出口）
    │    2  – 10  : uncraftingMatrix     （内部 9 格拆解预览；UncraftingSlot 包装，容器内槽位 0–8；
    │                                    GUI x 坐标 300000+i，屏幕外不可直接点击）
    │    11 – 19  : assemblyMatrix       （玩家可见 3×3 合成/重铸格；AssemblySlot = 纯 Slot）
    │    20 – 46  : 玩家主背包
    │    47 – 55  : 快捷栏
    ├─ clicked(int, int, ClickType, Player)         ← 所有取出动作的**唯一必经点**
    ├─ slotsChanged(Container)                      ← 重算拆解预览与代价
    └─ stillValid(Player)
  UncraftingResultSlot extends ResultSlot
    └─ onTake(Player, ItemStack)                    ← 出口槽实际被取走时的钩子（内部类，无法用 NeoForge 事件覆盖）
```

**实测签名（`javap -p`，发布版 4.8.3345）**：

```
public void clicked(int, int, net.minecraft.world.inventory.ClickType, net.minecraft.world.entity.player.Player);
public boolean stillValid(net.minecraft.world.entity.player.Player);
public void slotsChanged(net.minecraft.world.container.Container);
private final twilightforest.inventory.UncraftingContainer uncraftingMatrix;
public final net.minecraft.world.inventory.CraftingContainer assemblyMatrix;
private final net.minecraft.world.level.Level level;
private final net.minecraft.world.entity.player.Player player;
public net.minecraft.world.item.crafting.Recipe<?> storedGhostRecipe;
```

**关键机制（读源码 `UncraftingMenu.clicked` 得到）**：

1. 在 `clicked` 开头，若玩家点击的是**空的 assemblyMatrix 槽**且手上没拿东西，`slotNum -= 9` —— 点击被**重定向到 uncraftingMatrix**，最终 `super.clicked` 走的是拆解格。**因此限制逻辑必须同时覆盖重定向前后的两种槽位身份**。
2. `clicked` 中有三处 `return` 早退：重铸经验不足、`disableUncraftingOnly` 拦截、拆解经验不足、以及产物被 TF 标记（`isMarked`，受损部件）。
3. 玩家**只能**通过 `clicked` 拿到 `uncraftingMatrix` 里的物品（该矩阵不是玩家可见槽位的直接点击目标，只有重定向路径可达）。
4. **（M1 实读补充）一次重定向取物 = 一次完整拆解**：`UncraftingSlot#onTake` 按整次拆解扣一次经验、把剩余产物复制进 assemblyMatrix（此后重定向条件不再成立）、从 tinkerInput 扣 `numberOfInputItems` 个输入。
5. **（M1 实读补充）成功检测陷阱**：`UncraftingInputContainer#removeItem` 会回调 `slotsChanged(tinkerInput)` 清空并重灌拆解格——"取物成功"不能对比拆解格数量，只能对比 tinkerInput 数量递减。

### 2.3 暮色森林自带限制的不足（需求存在的理由）

| TF 自带配置 | 实际效果 | 源码证据 |
| --- | --- | --- |
| `disableUncraftingTable`（禁用整个拆解台） | 生效：`stillValid` 返回 false，交互被拒 | `TFConfig.disableEntireTable` 被 `UncraftingMenu#stillValid`、`UncraftingContainer#stillValid` 读取 |
| `disableUncrafting`（禁用普通配方拆解） | **形同虚设**：该字段在源码中**从未被读取**（只有声明、初始化与网络同步三处） | `grep -rn "disableUncrafting\b" src/main/java` 仅命中 `TFCommonConfig` 与 `SyncUncraftingTableConfigPacket` |
| `uncraftingXpCostMultiplier`（经验代价倍率） | 生效，但只影响"要花多少经验"，不限制频率 | `TFConfig.uncraftingXpCostMultiplier` 用于 `calculateUncraftingCost` |

结论：TF 只有"整个禁用"这一个粗粒度开关，**没有**冷却、耐久、次数等任何细粒度限制手段。本模组填补的正是这个空白。

### 2.4 暮色森林不使用 Mixin

TF 的自定义转换走独立库 jar `twilightforest-asm`（`FMLModType: LIBRARY`，`ICoreMod` 服务），其 10 个 transformer 全部针对**原版**类（雪、蘑菇、玩家 FOV、地图、拴绳等），`grep "twilightforest/"` 在 transformer 中只命中 `twilightforest/asmhooks/*` 钩子类名。TF 本体 jar 内**没有任何 mixin 配置**，`accesstransformer.cfg` 也未触碰拆解台相关类。

→ 不存在与 TF 自身字节码改造的冲突面；我们的 Mixin 注入点是"干净"的。

## 3. 逐方法技术闸门

### 3.1 闸门 A：全局冷却 —— ✅ 可行

| 项 | 结论 |
| --- | --- |
| 挂钩点 | Mixin `@Inject(method = "clicked", at = @At("HEAD"), cancellable = true)` |
| 判定 | 在 HEAD 处复刻 TF 的槽位重定向规则，判断本次点击是否会从 `uncraftingMatrix` 取走物品 |
| 状态存储 | NeoForge **Data Attachment**（挂 `ServerPlayer`）或世界级 **SavedData**；存"上次成功拆解的 gameTime" |
| 时间源 | `level.getGameTime()`（世界存档时间，随存档推进、服务器重启不重置） |
| 拦截效果 | `ci.cancel()` → 不执行任何物品移动，客户端下一次收包时槽位自然回滚，无需自建网络包 |
| 反馈 | `Player#displayClientMessage(Component, true)`（动作栏），显示剩余秒数 |

**为什么不用 NeoForge 事件**：`UncraftingResultSlot` 是 TF 的内部类，`onTake` 不触发任何 NeoForge 事件；`PlayerInteractEvent.RightClickBlock` 只能拦截**打开界面**，而玩家一次开界面可连续拆解多次，且关掉再开即可绕过。因此"取出动作"层面的限制**必须**用 Mixin。

### 3.2 闸门 B：禁止拆解 —— ✅ 可行（可能最简单）

与 A **共用同一个挂钩点**，只是判定改为"无条件拒绝从 `uncraftingMatrix` 取物"。附带的工程决定：

- **不**禁止打开界面：需求原文是"禁止**合成**"（即禁止拆解产出），允许预览更友好，也让玩家能确认为什么拿不出来。
- 可选加强（配置）：连界面一起禁止（在 `PlayerInteractEvent.RightClickBlock` 里对 `twilightforest:uncrafting_table` 取消并给提示）。

### 3.3 闸门 C：使用耐久 —— ✅ 可行（三种实现路径，见 §5 决策点 2）

需求"使用耐久"有两种解释，本模组支持**每座拆解台独立耐久**（更符合直觉），实现路径有三：

| 路径 | 做法 | 评估 |
| --- | --- | --- |
| C1 给拆解台挂 BlockEntity | 自己的 `BlockEntityType` + 在 mod bus 监听 **`BlockEntityTypeAddBlocksEvent`**（已实测存在于 NeoForge 21.1.248：`modify(BlockEntityType, Block...)`）把 `twilightforest:uncrafting_table` 加入；再用 Mixin 给 `UncraftingTableBlock` 织入 `EntityBlock#newBlockEntity` | **首选**。耐久随方块实体持久化，天然按方块位置隔离，不需要清理表；`UncraftingTableBlock` 目前**没有** BlockEntity，无冲突 |
| C2 世界级 SavedData 按 BlockPos 记耐久 | 无需 BlockEntity | 需要处理方块移除/卸载的清理，否则表无限增长；可作 C1 失败的降级方案 |
| C3 耐久写在掉落的方块物品上 | 用 `playerDestroy` + `ItemBlockState` 类数据组件往返 | 与"每座台独立耐久"语义有偏差（拆掉再放回会重置），仅在 C1 不可行时考虑 |

**耐久语义（待确认）**：

- 计数方式：**每次成功拆解扣 N 点**（默认 N=1），而不是"每件产物扣一次"——后者会让一个 9 格配方一次扣 9 点，与"使用耐久"的直觉不符。
- 耗尽行为：`destroy`（方块销毁，不掉落）或 `disable`（方块保留但失效）；默认 **destroy**，且必须给出前摇提示（对应全局纪律"永不静默删除玩家物品"——此处消耗的是方块耐久，仍会提前在动作栏警告剩余量）。

### 3.4 闸门 D：物品代价 —— ✅ 可行

在同一个挂钩点检查玩家物品栏中是否有指定物品，从中扣除。首版用**固定单一物品多项**的配置形式（`item_cost_entries` 列表，任一命中即可）。属于"额外方法"，不影响 A/B/C 的互斥结构。

## 5. 风险清单与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | 其他模组也 Mixin 同一个 `UncraftingMenu#clicked`，注入冲突 | 启动期 Mixin 应用失败 / 行为互斥 | 挂钩点收敛到 2 处（`clicked` 与 `UncraftingTableBlock`），Mixin 优先级留默认（1000），M0 用启动日志验证 `mixin apply` 成功；若冲突再调整 `priority` |
| R2 | `clicked` 是热路径，策略代码抛异常 | 玩家每次点击崩溃 | 策略入口整体 `try/catch`，异常时**放行**并每 60s 记一次警告（fail-open，保证不炸游戏） |
| R3 | `BlockEntityTypeAddBlocksEvent` 与 TF 的注册时序 | 方块实体不生成，耐久模式静默失效 | 该事件是 mod bus 事件、在方块注册完成后触发；M3 用 GameTest 断言 `level.getBlockEntity(pos) != null` |
| R4 | `stillValid` 的 8 格距离检查 | GameTest 里 mock 玩家不在测试 plot | 测试内 `mockPlayer.teleportTo(...)` 到方块旁（参考既有项目经验） |
| R5 | 拆解台配方有 `neoforge:conditions` 门槛（需 `maze_map_focus`） | 创意物品栏/测试环境里方块可能拿不到 | GameTest 直接用 `TFBlocks.UNCRAFTING_TABLE.get()` 放置，不依赖物品 |
| R6 | `maven.neoforged.net` 本机不可达期间无法新增依赖 | 无法引入新库 | 首版**零新增第三方依赖**（Mixin 由 NeoForge 自带），可全程离线构建 |
| R7 | Mixin refmap / 混淆名问题 | Mixin 静默不生效（最隐蔽的失败） | M0 用"故意写一个必然生效的最小注入 + 日志断言"验证链路，禁止跳过 |
| R8 | 与 TF 4.7.x 等旧版共存 | 老整合包崩 | 首版把 TF 版本范围设为 `[4.8.3345,)`，确认机制稳定后再单独评估放宽 |

## 6. 验证策略

| 层次 | 手段 | 覆盖内容 |
| --- | --- | --- |
| 签名层 | JDK21 `javap -cp <发布版 jar>` | 每次动 Mixin 目标前核对方法存在性（本文件 §2.2 已留基线） |
| 纯逻辑层 | 把冷却换算、耐久扣减、耗尽判定抽成不依赖 MC 的纯函数 | 便于快速回归（可选 JUnit，或直接在 GameTest 内断言） |
| 集成层 | `runGameTestServer` + GameTest | 见下表 |
| 人工层 | `runClient` | 动作栏文案、手感、界面观感（需要 RDPMouse，见 `AGENTS.md`） |

**GameTest 用例草案**：

| 用例 | 步骤 | 断言 |
| --- | --- | --- |
| G1 打开菜单 | mock 玩家传送到拆解台旁 → 调 `state.useWithoutItem(...)` 或 `player.openMenu(...)` | `player.containerMenu instanceof UncraftingMenu` |
| G2 放入可拆解物 | 给 `menu.slots.get(0).container` 设入 `minecraft:chest` 之类有配方物品 → 触发 `slotsChanged` | `uncraftingMatrix` 出现预览产物 |
| G3 冷却拦截 | 首次从拆解格成功取出 → 立刻再取 | 第二次点击后物品仍在格内（被拒） |
| G4 冷却过期 | 将时间戳回拨（或直接把 `gameTime` 偏移写进附件） → 再取 | 取出成功，时间戳被刷新 |
| G5 禁止模式 | `mode=DISABLED` 下取物 | 任何拆解格取物都被拒；界面仍可打开 |
| G6 耐久扣减 | `mode=DURABILITY`，连续取物 N 次 | 方块实体耐久按预期递减 |
| G7 耐久耗尽 | 把耐久设为 1 再取物 | 按 `on_deplete` 配置销毁/失效，无异常抛出 |
| G8 创造模式豁免 | `exempt_creative=true` 的创造玩家取物 | 不受限制 |

## 7. 结论

**可行，且实现成本低。**

- 需求的三条主线全部落在**同一个挂钩点**（`UncraftingMenu#clicked`）上，配一个配置枚举即可实现互斥；耐久模式额外需要一个 BlockEntity 与一个 mod bus 事件，均已实测存在。
- 暮色森林本体不使用 Mixin、不转换自身类，附属注入面干净。
- 前置依赖有两条可用下载路径（CurseMaven / ForgeCDN，SHA1 已核对一致），本机构建可离线完成。
- 主要工程风险集中在"Mixin 是否真的生效"这一件事上，已用 M0 的强制验证步骤覆盖。

**决策记录（2026-10-12，已确认）**：

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | modid | `uncraftinglimit` |
| 2 | 耐久模式语义 | **C1**：给拆解台挂 BlockEntity，每座台独立耐久；耐久耗尽 = **销毁方块**（`on_deplete = destroy`，带提前警告） |
| 3 | 物品代价（模式 D） | **纳入首版**；默认消耗暮色森林的火炬浆果（Torchberry），准确注册名在 M4 实现时核对，配置项为多物品列表 |
